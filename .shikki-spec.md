# One way to find a source root, one seam to inject a data root

## Phase 1 — Why

Four systems answer the same two questions — _where is the package / repo this code sits in?_ (a **source-tree root**, a build-layout fact) and _where does this process keep its data?_ (a **data root**, a runtime fact that must be injectable) — and none consumes the others. shikki has `ShikkiTestPaths` and `ShikkiPaths`; ShikkiCore has the `PathProviding` DI protocol with prod and sandbox implementations; shikki-plugin-api has `PathResolvers.searchUp(for:)` whose own header says "no project should re-implement the search loop"; and 52 shikki tests plus two CoreKit tests re-implement it anyway as counted `deletingLastPathComponent()` chains from `#filePath` — the shape shikki's #1668 review banned because a moved test breaks the count silently. BackendKit's ratchet helper, kagami and every future kit need the same two answers. The operator's review of CoreKit #21 asks the right question, and rev 1's panel did not dispute the answer — extract once into CoreKit, consume everywhere — it disputed the plan: a deferred plugin-api decision, a sweep that could delete the operator's live `~/.shikki`, an unmeasured baseline, an unaudited dependency edge, two implementations where the cited memory allows one, and waves whose gates did not name the tests they add. Rev 2 decides, measures, and sequences.

## Phase 2 — What (business rules)

- **BR-PATH-01 Two words for two roots.** `packageRoot` / `sourcesRoot` are source-tree facts found by walking up to a marker; `dataRoot` is the process's data directory, injected. The spec, the API and the doc comments never say "root" alone.
- **BR-PATH-02 CoreKit owns the primitives, layout-blind.** Runtime (`Sources/CoreKit/Paths/`): `PackageLayout.searchUp(from start: URL, for marker: String, maxDepth: Int = 32) -> URL?` (Optional, never throws, never guesses; the fleet's ONE marker walk; no caching — depth ≤ 32 directory probes per call is noise, and `preconditionFailure` semantics are left to callers); `PathProviding` moved verbatim from ShikkiCore (`shikkiHome` is renamed `dataRoot` in CoreKit; ShikkiCore's typealias keeps the old member through a protocol extension for one release); `ProdPaths(dataRoot:)` — the ONE conforming type (memory: prod and test differ only by the injected root); `PathsDIModule.register(dataRoot:in:)` — bootstrap API: the composition root passes the data root explicitly, registration is assert-once (a second `register` for `PathProviding` is a programming error caught by `Container`'s assert-once path, `Container.swift:354`), and the module logs one structured line `paths: dataRoot=<path> source=<caller>` at registration. Test-side (`Sources/CoreKitTestSupport/`): `TestPackagePaths` (landed in #21), `TestScratch(testsRoot:)` (`scratchRoot(scope:)` = `<testsRoot>/<scope>/<runID>/` — a per-process `runID` segment so parallel kagami runs never share a directory; `freshScratchDir`, the sanitizer), `TestSandbox.make(under testsRoot:) -> (paths: ProdPaths, sweep: () throws -> Void)` — a factory returning `ProdPaths` rooted at `<testsRoot>/.test-runs/<uuid>/` plus a sweeper, NOT a second `PathProviding` type; and `CountedDepthWalkRatchet.scan(testsRoot:) -> [String]` (patterns: `#filePath` followed within the same expression by `deletingLastPathComponent(` or `pathComponents.dropLast`; exemption by a `// path-ssot: primitive` line marker on the one implementing function, not by file name).
- **BR-PATH-03 Sweep is guarded, loud, and never near live data.** `TestSandbox.sweep()` and `TestScratch.removeScratchDir` refuse (throw `PathSweepError.outsideSandbox`) unless the target's standardized, symlink-resolved path has `.tests/` or `.test-runs/` as a segment AND ends in the UUID/runID segment they minted; they throw on filesystem errors (no `try?`), and log what they removed. `~/.shikki/.tests` is a valid testsRoot only because it carries the sentinel segment; `~/.shikki` itself can never be swept.
- **BR-PATH-04 The plugin-api decision is made: shape (b), structurally pinned.** shikki-plugin-api stays `dependencies: []` — plugins stay light, and CoreKit's twelve subsystems plus swift-crypto are not a plugin-time cost. `PathResolvers.searchUp` therefore remains a deliberate twin of `PackageLayout.searchUp`, and the twin is pinned **structurally**: both files carry a `// path-ssot: twin sha256=<hash of the normalized function body>` marker and `PathResolversTwinTests` (in CoreKit) fails when the two normalized bodies differ — drift is caught before it lands, not by a runtime parity test. Behavioural parity (T-07) covers marker present / absent / max depth / symlinked ancestor / permission-denied directory.
- **BR-PATH-05 Dependency edge, audited.** ShikkiCore does not depend on CoreKit today; W3 adds that edge (ShikkiCore → CoreKit 0.10.0, pulling swift-crypto). This is the intended layering — CoreKit is the base every kit stands on, shikki already depends on both — and the cost is stated: ShikkiCore's resolve graph grows by CoreKit + swift-crypto; no cycle is possible because CoreKit depends on nothing of the fleet. ShikkiCore's move ships as `0.2.0` (minor: a public protocol relocates; typealias + `@available(*, deprecated, renamed:)` on every relocated symbol; a `Paths` extension file keeps ShikkiCore-side extensions compiling), and the deletion is owned: backlog `5b8e2c4a-followup` filed at W3 delivery with the release after 0.2.0 as its deadline, plus a ratchet in ShikkiCore (`DeprecatedPathAliasesRatchetTests`) that fails once that release is tagged.
- **BR-PATH-06 Kits consume; the layout stays where it belongs.** shikki: `ShikkiTestPaths` keeps what is shikki (`sampleWorkspaceID/Root`, `sampleProjectDir`, `flowsRoot(scope:)`, `specsDir(scope:)`) and forwards `testsRoot`/`scratchRoot`/`freshScratchDir`/`removeScratchDir` to `TestScratch(testsRoot: ShikkiPaths.shikkiHomeRoot/.tests)` and `packageRoot`/`sourcesRoot` to `TestPackagePaths` — parity asserted on **normalized** paths (`standardizedFileURL.resolvingSymlinksInPath().path`, trailing slash stripped), never on bytes; `ShikkiRootResolver` stays shikki's (it knows `SHIKKI_ROOT` and `~/.shikki`) and uses `PackageLayout.searchUp` for its marker walks; `ShikkiPaths` keeps the layout. ShikkiCore: typealiases (BR-PATH-05). BackendKit: `ConnectionInjectionRatchet.scan(sourcesRoot: TestPackagePaths.sourcesRoot(ofModule:))`. kagami, NetKit: the ratchet is installed in their test trees in W6 with baseline 0 so a first copy cannot appear.
- **BR-PATH-07 Ratchets with written baselines.** `CountedDepthWalkRatchet` baselines are per-file JSON next to the test (`Tests/<target>/Fixtures/counted-depth-walk-baseline.json`, the shape of shikki's `personal-fixture-baseline.json`): shikki starts at **43 files / 52 sites** (listed in the baseline file at W3), CoreKit at 1 (`DeviceCapacitySnapshotTests`, fixed in W1 → 0), ShikkiCore at 2, kagami/NetKit/BackendKit at 0; counts only go down, a file not in the baseline must be clean, and `shi pre-pr` rejects an increase because the test fails.
- **BR-PATH-08 Operability.** `shi doctor --check paths` prints the registered data root, its source, the testsRoot in effect and whether the sweep sentinel holds; misregistration is a red check, not a silent wrong directory.

## Phase 4 — Test plan

When `TestPackagePaths.packageRoot(fromTestFile:)` is called from a test three directories deep and from one moved two directories up:
Then both return the same package root — the nearest `Package.swift`, not a counted depth (T-01).

When `PackageLayout.searchUp(from:for:)` runs inside a package, outside any package, through a symlinked ancestor, and against a permission-denied directory:
Then it returns the package root, nil, the root through the symlink, and nil without throwing (T-02).

When `PathsDIModule.register(dataRoot:in:)` runs, then runs again on the same `Container`:
Then the first registration logs `paths: dataRoot=… source=…` and `resolve("flows")` is under that root; the second traps assert-once (T-03).

When `TestSandbox.make(under:)` is swept, and when `sweep` is aimed (by a test double) at a path without the `.test-runs/<uuid>` sentinel:
Then the sandbox subtree is removed and logged; the second call throws `PathSweepError.outsideSandbox` and removes nothing (T-04).

When two `TestScratch(testsRoot:)` instances in two processes ask for `scratchRoot(scope: "x")`:
Then the directories differ by `runID` and neither run sees the other's files (T-05).

When shikki builds against CoreKit 0.10.0 and ShikkiCore 0.2.0:
Then `ShikkiTestPaths.packageRoot`/`sourcesRoot`/`testsRoot`/`scratchRoot` equal today's on normalized paths (T-06, parity) and every existing ratchet baseline is unchanged.

When ShikkiCore builds with the typealiases:
Then the `ShikkiCorePaths` scope is green unchanged, every alias use emits a deprecation warning, and `DeprecatedPathAliasesRatchetTests` passes until the release after 0.2.0 is tagged (T-07).

When a test file outside the marked primitive contains `#filePath` … `deletingLastPathComponent(` or `pathComponents.dropLast`:
Then `CountedDepthWalkRatchet` names `file:line`, the per-file count never exceeds the baseline file, and an unlisted file must be clean (T-08).

When the normalized bodies of `PackageLayout.searchUp` and `PathResolvers.searchUp` differ:
Then `PathResolversTwinTests` fails naming both files (T-09).

When `shi doctor --check paths` runs with a registered data root under a sandbox and with none registered:
Then it prints root, source and sentinel status, and is red under `--strict` when nothing is registered (T-10).
